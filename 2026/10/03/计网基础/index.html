2.2 无状态与连接复用

HTTP 无状态：协议本身不自动维护用户业务身份；应用通过 Cookie、Session、Token 等关联请求。

连接复用：多个请求使用已有连接，以减少建连开销。HTTP/1.1 默认支持持久连接，并非每次都必须发送 Connection: keep-alive。

概念 作用
HTTP 持久连接 复用连接，减少握手开销
TCP Keepalive 对长时间空闲的连接进行存活探测
登录 Session 保存或关联应用层的登录状态

无状态不意味着不能复用连接，也不意味着服务器不能保存数据。

2.3 方法、安全性与幂等

方法 主要语义 安全方法 幂等
GET 获取资源 是 是
HEAD 获取类似 GET 的头部，不返回响应内容 是 是
OPTIONS 查询通信选项 是 是
POST 提交数据，由资源定义处理行为 否 不保证
PUT 创建或替换指定资源的状态 否 是
PATCH 部分修改资源 否 不保证
DELETE 删除目标资源的关联 否 是

“安全方法”表示客户端没有要求改变资源状态，不表示没有日志等附带效果，也不表示通信经过加密。

“幂等”表示相同请求重复执行，其预期效果与执行一次相同，不要求每次响应完全一致。

  • 将昵称设置为 Alice：重复执行，最终昵称不变。
  • 将余额增加 100：重复执行可能累加，不保证幂等。
  • DELETE 第一次返回 204、第二次返回 404，仍可符合幂等语义。

POST 创建订单超时，不代表订单没有创建。自动重试前需要确认业务幂等性，或使用幂等键、结果查询等机制。

GET、POST 都能通过 HTTPS 加密。POST 本身不会自动提供安全性；URL 参数还容易进入历史记录和访问日志。

2.4 HTTP 版本比较

版本 主要机制 关键限制
HTTP/1.1 文本报文、持久连接、分块传输 流水线响应必须按请求顺序返回，可能产生应用层队头阻塞
HTTP/2 二进制帧、多路复用、HPACK 头部压缩 底层 TCP 丢包仍可能阻塞多个流
HTTP/3 QUIC、多路复用、QPACK 头部压缩 仍受拥塞、带宽以及各流自身丢包影响

HTTP/2 允许不同流的帧交错传输，但 TCP 必须有序交付字节。缺失字节未补齐时，后续已到达数据可能无法向上交付。

QUIC 按流提供可靠、有序交付，一个流的数据丢失通常不会直接阻塞其他流交付自己的数据，但各流仍共享网络资源和拥塞控制。

3. HTTPS 与 TLS

3.1 HTTPS 提供什么

  • 机密性：防止中间人直接读取 HTTP 内容。
  • 完整性：检测传输内容被篡改。
  • 身份认证：验证所连接服务器的身份。

普通网站通常只认证服务器；mTLS 还要求客户端提供证书。TLS 身份认证不等于用户登录认证。

3.2 TLS 1.3 完整握手

以下以运行在 TCP 上、使用服务器证书和 ECDHE 的常规完整握手为例，不涉及 PSK 恢复、0-RTT、HelloRetryRequest、客户端证书或 ECH。

第一步：客户端发送 ClientHello（明文）

字段或扩展 内容
legacy_version TLS 1.3 ClientHello 中必须设置为 0x0303，即 TLS 1.2 的版本编号；它不代表最终协商版本
supported_versions 声明实际支持的版本，TLS 1.3 对应 0x0304
cipher_suites 提供支持的密码套件；TLS 1.3 套件指定 AEAD 算法及 HKDF 使用的哈希算法，例如 TLS_AES_128_GCM_SHA256
server_name（SNI） 指明希望访问的服务器主机名
application_layer_protocol_negotiation（ALPN） 声明支持的应用协议，例如 h2、http/1.1
key_share 提供支持组对应的临时公钥等密钥交换参数，临时私钥保留在本地

TLS 1.3 的签名算法和密钥交换组通过各自的协商字段确定，不包含在上述密码套件名称中。

第二步：服务器发送 ServerHello（明文），双方派生握手密钥

服务器选择协议版本、密码套件和密钥交换组，通过 supported_versions 确认 TLS 1.3，并通过 key_share 返回自己的临时公钥。

双方使用各自的临时私钥和对方的临时公钥，独立计算出相同的 ECDHE 共享秘密（shared secret），私钥和共享秘密都不直接发送。

随后按 TLS 1.3 的 HKDF 密钥派生流程处理：

  • 本例不使用 PSK，先以规定的全零输入生成 Early Secret。
  • 将 Early Secret 的派生值与 ECDHE 共享秘密通过 HKDF-Extract 结合，得到 Handshake Secret。
  • 从 Handshake Secret 分别派生客户端和服务端的 handshake traffic secret，绑定截至 ServerHello（包含它）的握手记录哈希。
  • 从各方向的 traffic secret 分别派生记录加密使用的 key、IV，以及计算 Finished 使用的 finished_key。
  • Handshake Secret 还通过另一条 HKDF 派生路径生成 Master Secret，供后续派生应用流量秘密。

共享秘密、Handshake Secret、Master Secret、traffic secret 与实际加密 key 是不同的值；客户端和服务端的发送方向也使用不同密钥。

第三步：服务器发送加密握手消息

ServerHello 之后，服务器使用服务端方向的握手流量密钥保护以下消息：

消息 作用
EncryptedExtensions 返回相应扩展结果，例如通过 ALPN 选择 h2
Certificate 发送服务器证书链；TLS 1.3 中此消息受到加密保护
CertificateVerify 使用证书对应私钥，对包含握手记录哈希的规定结构签名，证明私钥持有权并绑定本次握手
Finished 使用专门派生的 finished_key，对此前握手记录哈希计算 HMAC，用于验证握手记录和密钥的一致性

CertificateVerify 的签名输入包含固定前缀、上下文字符串、分隔符和握手记录哈希。握手记录也包括此前受加密保护的握手消息在解密后的内容，不仅限于在线路上明文发送的消息。

这里使用发送方对应方向的 handshake traffic secret。记录哈希不包含当前这条 Finished；finished_key 用于计算 HMAC，不用于加密 TLS 记录。

第四步：客户端验证并发送 Finished

客户端使用服务端握手流量密钥解密消息，验证证书链是否受信任、证书有效期及主机名是否匹配，再验证 CertificateVerify 签名和服务端 Finished。

验证通过后，客户端使用客户端方向的 finished_key 计算自己的 Finished，并用客户端握手流量密钥加密发送。它的握手记录包含此前收到的服务器 Finished。

第五步：按方向切换到应用流量密钥

双方从 Master Secret 派生各自方向的初始 application traffic secret，绑定截至服务器 Finished（包含它）的握手记录哈希，再从中派生应用数据加密使用的 key、IV。这一步不需要等待客户端 Finished 才具备派生条件。

  • 服务器 Finished 本身仍由服务器握手流量密钥保护；发送后，服务器可以使用服务器应用流量密钥发送后续应用数据。
  • 客户端验证服务器 Finished 后，可以使用服务器应用流量密钥接收后续服务器应用数据。
  • 客户端 Finished 仍由客户端握手流量密钥保护；发送后，客户端可以使用客户端应用流量密钥发送 HTTP 请求等应用数据。
  • 服务器接收并验证客户端 Finished 后，使用客户端应用流量密钥处理后续客户端应用数据。

相关握手秘密和密钥在不再需要后清除。例如，服务器已切换自己的发送方向时，仍需保留接收客户端 Finished 所需的握手密钥。应用流量密钥后续还可以通过 KeyUpdate 更新。

技术 主要用途
ECDHE 等 密钥交换
RSA、ECDSA 等签名 身份证明和握手认证
AES-GCM、ChaCha20-Poly1305 加密应用数据并校验完整性

现代 HTTPS 不能统一解释成“客户端生成对称密钥，再用服务器公钥加密发送”。ECDHE/TLS 1.3 使用不同机制，并可提供前向保密：长期私钥后来泄露，通常也无法单凭该私钥解密过去的会话。

3.3 SNI、ALPN 与可见信息

名称 所在位置 作用
SNI TLS 握手 指明希望访问的主机名
ALPN TLS 握手 协商 HTTP/2 等应用协议
Host / :authority HTTP 请求 标识请求面向的主机及端口

HTTPS 会保护 HTTP 路径、查询参数、Headers、Cookie 和正文。旁观者仍可能看到 IP、端口、长度和通信时序。

没有 ECH 时，SNI 通常可见；DNS 是否可见取决于是否使用加密 DNS。TLS 1.3 的服务器证书位于加密握手中，不能假设抓包总能直接看到。

TLS 会话恢复能降低重连开销。0-RTT 早期数据有重放风险，不应随意用于扣款、创建订单等操作。TLS 会话恢复与应用登录 Session 是不同机制。

3.4 TLS 指纹与自动化识别

Python 请求库与 TLS 实现

requests、aiohttp、httpx 的默认 HTTPS 路径通常通过 Python ssl 实现 TLS。ssl 使用 Python 构建或运行时所链接的 OpenSSL；该库可能来自系统，也可能由 Python 发行版提供，不能一概称为“操作系统自带 OpenSSL”。

6. Session、Token 与登录状态

6.1 典型 Session 流程

概念 职责
Cookie 浏览器管理、按规则发送的数据
Session 应用维护的会话状态机制
Session ID 关联请求与会话的标识
Token 认证或授权凭据，可为不透明随机值或结构化数据

Session 是应用层机制，不是 HTTP 内置功能。会话状态可以保存在内存、Redis、数据库等位置。

6.2 生命周期与部署

  • 空闲超时：一段时间未活动后失效。
  • 绝对超时：达到最长有效期后失效。
  • 注销失效：退出登录后撤销会话。
  • 主动撤销：改密码、风控或管理员操作后失效。

Cookie 到期与服务端 Session 到期是两套机制。 浏览器仍有 Cookie 不代表会话有效；仅删除浏览器 Cookie 也不等于撤销泄露的 Session ID。

登录或权限提升后通常应更新 Session ID。多实例部署要处理会话共享问题，否则可能出现“在 A 登录成功，到 B 又未登录”。

6.3 JWT 与客户端 Session

  • Bearer Token 不一定是 JWT；随机 Token 也可能需要服务端查询。
  • 普通签名 JWT 的内容未加密，签名主要用于校验真实性和完整性。
  • JWT 可以存储在 Cookie 中；二者不是互斥方案。
  • JWT 仍需要处理过期、撤销、凭据泄露等问题。
  • Python requests.Session() 主要管理客户端 Cookie 和连接池，不等于服务端登录 Session。

8. TCP 三次握手：为什么偏偏是三次

8.1 三次握手流程

TCP 通过三次握手交换并确认双方的初始序列号，为可靠传输建立连接。设客户端初始序列号为 x，服务端为 y：

次数 方向与报文 含义 状态
第一次 客户端 → 服务端：SYN，seq=x 我要建立连接，初始序列号是 x 客户端进入 SYN_SENT
第二次 服务端 → 客户端：SYN+ACK，seq=y，ack=x+1 收到你的 SYN；我的初始序列号是 y 服务端本次连接进入 SYN_RECEIVED
第三次 客户端 → 服务端：ACK，seq=x+1，ack=y+1 收到你的 SYN，可以开始传输 客户端收到有效 SYN+ACK 后进入 ESTABLISHED；服务端收到最终 ACK 后进入 ESTABLISHED

记忆顺序：SYN → SYN+ACK → ACK。

SYN 占用一个序列号，所以确认号要加 1；纯 ACK 不占用序列号。TCP 序号按字节计算，ack 表示期待对方接下来发送的字节序号，不是包编号。

8.2 为什么两次不够、四次没必要

两次不够： 服务端发送 SYN+ACK 后，还不知道客户端是否收到了自己的初始序列号。第三次 ACK 完成这个确认，避免仅收到连接请求就认定连接建立。

这也有助于处理延迟到达的旧 SYN：服务端必须等待对本次序列号的有效确认，不能只凭旧请求建立连接；但等待期间仍可能占用半连接资源。

四次没必要： 双方各有一个 SYN 需要对方确认。服务端把“确认客户端 SYN”和“发送自己的 SYN”合并成 SYN+ACK，四个逻辑动作就变成三个报文。

面试回答重点是：交换并确认双方初始序列号，服务端的 SYN 与 ACK 可以合并。 “确认双方收发能力”可以作为辅助理解。

8.3 常见追问

问题 面试回答
第三次 ACK 丢失怎么办？ 服务端通常超时重传 SYN+ACK，客户端再次回复 ACK；后续携带有效 ACK 的数据也可能完成建连。一直没有有效确认则超时放弃。
第三次 ACK 能携带数据吗？ 可以，但不保证实际合并发送。普通 HTTPS 还需进行 TLS 握手，不能直接发送 HTTP 明文请求。
握手大约耗时多久？ 无重传时，从客户端发 SYN 到收到 SYN+ACK，约 1 RTT；HTTPS 还要考虑 TLS 握手。
爬虫怎样减少握手开销？ 在循环外创建 Session，复用连接池，读完响应并控制并发，让多个请求使用已有连接。具体示例见第 9 章。

9. 爬虫如何减少握手次数并节省资源

9.1 让多次请求复用已经建立的连接

普通 TCP 客户端不能自行把三次握手改成两次。爬虫减少握手次数的主要办法是：减少新建连接，让同一连接承载后续多个请求。

以同一 HTTPS 站点上的 1000 次顺序请求为例：

请求方式 TCP 建连次数 TLS 握手次数
每个请求都新建并关闭连接 约 1000 次 约 1000 次
始终复用一条健康连接的理想情况 1 次 1 次
实际运行中总共新建 K 条连接 K 次 通常随这些新连接发生

实际连接数受并发、服务端关闭策略、连接空闲时间、代理和网络错误等影响，不能保证所有请求永远只使用一条连接。

在新建 TCP、进行常规 TLS 1.3 完整握手且无重传的简化场景下，开始发送普通 HTTP 请求前的连接建立开销约为 1 RTT 的 TCP + 1 RTT 的 TLS。若 RTT 为 50 ms，每次重复建连约增加 100 ms 的等待，不包含 DNS、业务处理和正文传输。

连接复用还能减少握手报文、TLS 计算、socket 创建和关闭、临时端口及内核连接状态的反复分配。

9.2 requests：在循环外创建 Session

连续调用独立的 requests.get() 通常不会跨调用保留可复用的连接池。应让同一个 requests.Session() 覆盖一批请求的整个生命周期。

示例中的关键点：

  • Session 在循环外创建，请求通过同一个连接池发送。
  • 示例使用默认的非流式响应，Requests 会读取正文，连接因此有机会归还池并被复用。
  • timeout=(5, 20) 分别指定连接超时和读取超时；读取超时主要约束等待数据的间隔，不是整个下载的总时限。
  • 退出 Session 上下文时，关闭其连接池，释放资源。
  • 实际爬虫可在读取正文后进行解析和保存；此处只演示连接生命周期。

不要在每次循环中重新创建 Session，也不要在每个请求后关闭整个 Session，否则连接池无法持续复用。

HTTP/1.1 默认支持持久连接。仅添加 Connection: keep-alive，不能替代客户端连接池和正确的对象生命周期。HTTP/2、HTTP/3 也不应发送这种连接专用头部。

9.3 正确读取和释放响应

连接只有在当前响应得到妥善处理后，才能供后续请求使用。

场景 建议
普通网页 完整读取正文，再继续下一次请求
大文件或大响应 使用流式读取，按块处理，避免一次全部载入内存
stream=True 尽量读完响应体；使用上下文管理器确保异常时也能关闭响应
提前停止流式读取 关闭响应以释放资源，但底层连接可能被丢弃，不能保证继续复用

“关闭响应”与“关闭整个 Session”是两个动作。未读完正文就关闭响应，虽然可以避免资源泄漏，却未必能保留这条连接。

9.4 连接池与并发要一起控制

HTTP/1.1 的常见客户端通常不会在一条连接上同时处理多个独立请求。提高并发时，连接池可能创建多条连接，并在后续任务之间复用它们。

  • 根据站点响应速度和本机资源设置有限并发，不要一次启动无限任务。
  • 同时设置合理的连接数、空闲连接保留数量和超时，避免长期持有过多 socket。
  • 在 requests/urllib3 中，仅设置 pool_maxsize、同时保持默认的 pool_block=False，不一定能限制瞬时并发连接数；需要结合 pool_block=True 和任务并发上限。
  • 多线程使用 Requests 时，不要假定可随意并发修改同一个 Session；可让固定数量的工作线程各自长期复用自己的 Session，并在结束时关闭。
  • 使用 httpx.AsyncClient 或 aiohttp.ClientSession 时，在同一异步任务生命周期内复用客户端，配合连接限制和任务并发控制，避免在每个任务里新建客户端。
  • 不同登录账户应隔离 Cookie 和会话状态，不能为了复用而混用身份。

连接复用降低重复建连成本；并发控制限制峰值资源占用，两者需要同时考虑。

9.5 HTTP/2、TLS 恢复和 Keepalive 的区别

机制 能减少什么 边界
HTTP 持久连接与连接池 重复 TCP 建连；HTTPS 下也通常减少重复 TLS 握手 需要已有连接仍可用
HTTP/2 多路复用 多个并发请求为此额外创建连接的需要 需要客户端与服务端支持并协商成功
TLS 会话恢复 新建安全连接的部分认证和计算成本 仍可能需要新建 TCP 连接，不等于免握手
TCP Keepalive 探测长时间空闲连接是否失效 不是 HTTP 请求复用机制

Requests 默认使用 HTTP/1.1。需要 HTTP/2 时，可选择支持它的客户端，例如配置启用 HTTP/2 的 HTTPX；是否实际使用 HTTP/2，还取决于服务端和协商结果。

HTTP/3 使用 QUIC/UDP，不适用本章的 TCP 三次握手流程。

9.6 为什么已经用了 Session，仍然频繁握手

常见原因包括：

  • 服务端设置了连接空闲超时或每条连接的请求数上限。
  • 服务端主动关闭连接，或返回 Connection: close。
  • 流式响应未读完，连接无法正常归还池。
  • 频繁切换域名、端口、代理或 TLS 配置，导致请求分散到不同连接池。
  • 并发需求超过已有连接数量，客户端需要创建更多连接。
  • 代理或网络设备关闭了空闲连接，客户端复用时发现它已经失效。

优先检查连接是否真正复用，以及没有复用的原因。对失效连接重试时，还要考虑请求幂等性，不能仅因超时就盲目重发可能产生副作用的请求。

一、HTTP 协议核心基础（超文本传输协议）

1.1 协议定义与核心特性

HTTP（HyperText Transfer Protocol，超文本传输协议），是基于 TCP、面向请求 - 响应模式、无状态无连接的应用层协议，默认端口 80。

四大核心特性（考试 + 实操高频）

1. 基于 TCP 可靠传输：

HTTP 本身无传输能力，依赖 TCP 三次握手建立连接，四次挥手断开连接，保证数据不丢失、不错乱。

2. 无状态（核心重点）

服务器不存储任何客户端请求状态信息，每次请求都是独立隔离的。

通俗案例：浏览器两次访问同一网站，服务器无法识别是同一个客户端，不会记录用户行为，需依靠 Cookie、Session、Token 实现状态保持。

3. 无连接（版本迭代优化）

  • HTTP/1.0：单次请求单次连接，一次请求响应完成，立即断开 TCP 连接，频繁请求需反复握手，效率极低。
  • HTTP/1.1：默认开启持久连接（长连接），一次 TCP 连接可传输多次 HTTP 请求，通过请求头参数控制连接状态。

4. 明文传输：

所有请求、响应数据裸奔传输，无加密，可被抓包、窃听、篡改，存在严重安全漏洞（HTTPS 解决此问题）。

1.2 HTTP 主流版本核心区别

协议版本 核心优化 连接机制 传输特点
HTTP/1.0 基础规范 短连接为主 单次请求一次 TCP 连接，资源请求耗时高
HTTP/1.1 行业通用标准 默认长连接 支持管道请求、缓存优化、断点续传，目前最普及
HTTP/2.0 多路复用 单连接多流 二进制帧传输、并发请求无阻塞、头部压缩
HTTP/3.0 全新底层 基于 UDP 解决 TCP 队头阻塞，极速传输

四、HTTPS 协议深度详解（加密核心 + 握手全流程）

4.1 HTTPS 基础定义

HTTPS（HyperText Transfer Protocol Secure）= HTTP + SSL/TLS 安全加密层

  • 默认端口：443
  • 核心作用：解决 HTTP 明文传输漏洞，实现传输加密、数据完整性校验、服务器身份认证
  • 底层逻辑：HTTP 应用层数据，先经过 SSL/TLS 加密，再通过 TCP 传输

4.2 HTTP 与 HTTPS 核心对比（考点汇总）

对比维度 HTTP HTTPS
端口 80 443
传输方式 明文传输 对称 + 非对称混合加密
安全性 极低，可窃听篡改 极高，防窃听、防篡改、防伪造
握手流程 仅 TCP 三次握手 TCP 握手 + SSL/TLS 握手
证书要求 无 必须 CA 数字证书
性能 传输快、无加密开销 略有加密损耗，安全性优先

4.3 HTTPS 加密核心原理（双加密机制）

HTTPS 采用混合加密模式，结合两种加密方式的优势，兼顾安全与速度：

1. 非对称加密（RSA）： 加密效率慢、安全性极高

用途：握手阶段加密传输会话密钥、验证服务器证书合法性

2. 对称加密（AES）： 加密效率快、适合大量数据传输

用途：数据传输阶段加密所有 HTTP 报文

4.4 HTTPS 完整握手流程（7 步全拆解，重点难点）

HTTPS 通信分为 TCP 握手和 SSL/TLS 握手两个阶段，全程 7 步，是面试、考试高频难点：

前置：TCP 三次握手（建立底层可靠连接）

SSL/TLS 四次握手（核心加密协商流程）

1. 客户端→服务器：Client Hello

客户端发送：支持的 TLS 版本、加密套件列表、客户端随机数（Client Random）

2. 服务器→客户端：Server Hello

服务器确认：选定的 TLS 版本、加密套件、服务器随机数（Server Random）

3. 服务器→客户端：证书下发

服务器发送 CA 数字证书（包含服务器公钥、域名、签名、有效期）

4. 客户端：证书校验

客户端验证证书合法性：CA 签名是否有效、域名是否匹配、是否过期、是否被吊销

校验失败：直接终止连接，提示不安全网站

5. 客户端→服务器：发送预主密钥

客户端生成预主密钥（Pre-Master Secret），用服务器公钥加密后发送

6. 双方生成统一会话密钥

客户端 + 服务器，通过「客户端随机数 + 服务器随机数 + 预主密钥」，独立生成一致的对称会话密钥

7. 加密通信开启

后续所有 HTTP 请求、响应数据，均通过会话密钥对称加密传输

4.5 核心参数详解：三个随机数的作用

1. Client Random、Server Random、Pre-Master Secret

三者组合生成唯一会话密钥，保证：

  • 每次 HTTPS 会话密钥不重复
  • 即使单次密钥泄露，不影响其他会话
  • 彻底杜绝固定密钥破解风险

4.6 HTTPS 数据完整性校验机制

SSL/TLS 内置 MAC 消息认证码，传输数据时附带校验哈希值：

  • 数据传输后，接收方校验哈希
  • 数据被篡改→哈希不匹配→直接丢弃数据，拒绝响应

七、核心面试 / 考试简答题汇总

1. 简述 HTTP 无状态特性及解决方案

HTTP 无状态，是指协议本身不会自动把多次请求关联为同一个用户的业务会话。服务器收到请求后，需要根据请求携带的信息识别用户；无状态不代表服务器不能保存数据，也不代表每次请求都要重新建立连接。

常见的状态保持方案：

  • Cookie + Session：登录成功后，服务器保存会话状态，并通过 Set-Cookie 下发 Session ID。浏览器后续向符合条件的地址发送请求时携带该 Cookie，服务器根据 Session ID 查找会话、识别用户。
  • Token：登录后签发认证凭据，客户端后续通过 Authorization 或 Cookie 携带，服务器验证其有效性。Token 可以是随机字符串，也可以是 JWT。

Cookie 是客户端保存和发送数据的机制，Session 是应用维护会话状态的机制，两者可以配合使用。Python 的 requests.Session() 主要管理客户端 Cookie 和连接池，与服务端登录 Session 不是同一概念。

2. 对比 HTTP/1.0、HTTP/1.1、HTTP/2.0 的区别

对比维度 HTTP/1.0 HTTP/1.1 HTTP/2.0
报文形式 文本报文 文本报文 二进制帧
连接使用 默认非持久连接，可通过扩展复用 默认持久连接 通常在同一连接上承载多个流

主要限制 频繁建连开销较大 同一连接上存在应用层队头阻塞 底层 TCP 丢包仍可能阻塞多个流

面试时可以概括为：HTTP/1.0 默认短连接，HTTP/1.1 默认长连接，HTTP/2 通过二进制分帧、多路复用和头部压缩提高连接利用率。

HTTP/2 解除了 HTTP/1.1 流水线中“后一个响应必须等待前一个响应”的顺序限制，但 TCP 仍要求字节按序交付，因此没有消除 TCP 层的队头阻塞。

3. 详细说明 GET 和 POST 的五大核心区别

  1. 请求语义与幂等性：GET 用于获取资源，按协议语义属于安全、幂等的方法；POST 用于提交内容，由目标资源执行处理，不保证幂等。例如，重复 GET 查询订单不会要求新增订单，重复 POST 创建订单则可能重复创建。“安全方法”指不要求改变资源状态，与是否加密无关。
  2. 参数承载方式：GET 通常通过 URL 查询参数传参，POST 通常通过请求体传参，但 POST 也能携带 URL 查询参数。GET 请求体没有通用定义的语义，存在兼容性问题，实际开发不应依赖它。
  3. 缓存行为：GET 响应通常可以缓存，实际是否缓存受状态码、缓存头等条件控制；POST 响应需要满足明确的缓存条件，并取决于客户端或缓存实现支持，实际较少缓存，不能说“绝对不能缓存”。
  4. 长度限制：HTTP 没有统一规定 GET 只能传多少字节，也没有规定 POST 无限大。GET 常受 URL 长度限制，POST 常受请求体大小限制；具体上限由浏览器、代理、服务器及应用配置决定。
  5. 信息暴露与传输安全：GET 的 URL 参数更容易进入浏览器历史记录、访问日志等位置；POST 请求体通常不出现在地址栏，但可能被日志记录，也不会自动加密。两者都需要 HTTPS 来保护传输中的内容。

对爬虫而言，GET 一般适合查询和获取页面；POST 常用于登录、表单提交等操作。POST 超时不代表服务器未执行，自动重试前应确认业务幂等性，避免重复提交。

4. 完整描述 HTTPS 握手全过程

以 HTTP/1.1 或 HTTP/2 使用新建 TCP 连接、TLS 1.3、服务器证书和 ECDHE 的常规完整握手 为例，不考虑会话恢复和客户端证书：

  1. 先建立 TCP 连接：客户端和服务器完成 TCP 三次握手，为后续 TLS 消息提供可靠传输。
  2. 客户端发送 ClientHello：声明支持的 TLS 版本、密码套件等信息，提供客户端随机数和用于 ECDHE 的临时公钥。
  3. 服务器发送 ServerHello：选定版本、密码套件等参数，提供服务器随机数和自己的临时公钥。双方用各自的临时私钥与对方的临时公钥计算相同的共享秘密，再通过密钥派生算法生成握手密钥。共享秘密本身不会直接在网络上传输。
  4. 服务器发送身份与握手证明：用握手密钥保护后续消息，包括证书链、CertificateVerify 签名和 Finished。证书链用于验证身份，签名证明服务器持有对应私钥，Finished 用于验证握手记录和密钥的一致性。
  5. 客户端验证并发送 Finished：校验证书链是否受信任、域名和有效期是否匹配，验证服务器签名及 Finished。通过后发送自己的 Finished；服务器收到后进行验证。
  6. 使用应用流量密钥传输 HTTP：双方按 TLS 1.3 的规则派生并启用各发送方向的应用流量密钥，使用对称加密保护 HTTP 请求和响应，同时校验完整性。

通常可概括为：先 TCP 建连，再协商 TLS 参数和密钥、验证服务器身份，最后加密传输 HTTP 数据。 常规 TLS 1.3 完整握手在 TCP 建连之后还需约 1 个 RTT，TLS 消息不等于固定数量的 TCP 报文。

若面试官指定传统 TLS 1.2 的 RSA 密钥交换：客户端验证服务器证书后，生成预主密钥，用证书中的 RSA 公钥加密发送；服务器用私钥解密，双方结合随机数派生密钥，并通过 Finished 验证握手。TLS 1.2 也支持 ECDHE，TLS 1.3 已移除上述 RSA 密钥传输方式。

已建立的 HTTPS 连接可以复用，多次 HTTP 请求不必重复 TCP 和 TLS 握手。HTTP/3 使用 QUIC，并将 TLS 1.3 握手集成其中，不经过 TCP 三次握手。

5. 简述 HTTPS 混合加密的工作原理

HTTPS 结合公钥密码机制与对称密码机制，分别解决身份认证、密钥协商和高效数据保护的问题：

  • 身份认证：客户端验证服务器证书；服务器通过 RSA、ECDSA 等签名算法证明持有证书对应的私钥，并将身份与本次握手绑定。
  • 密钥协商：现代 TLS 通常通过 ECDHE 等方式协商共享秘密，再派生通信密钥。RSA 可以用于签名，并不意味着它负责加密传输会话密钥。
  • 数据保护：使用 AES-GCM、ChaCha20-Poly1305 等对称 AEAD 算法加密 HTTP 数据，并验证数据完整性。

这样既能在不直接传输共享秘密的情况下建立可信的加密通道，又能利用对称算法高效处理大量数据。使用 ECDHE 并妥善清除临时密钥，还能提供前向保密：服务器长期私钥后来泄露，通常也无法仅凭该私钥解密此前录制的会话。

6. 301 和 302 重定向的区别

对比维度 301 Moved Permanently 302 Found
核心含义 资源永久迁移 资源临时位于另一个地址
常见场景 网站迁移、旧地址永久替换 临时跳转、未登录时跳转登录页
后续访问 客户端可以采用新的地址 后续请求仍应使用原地址
缓存 可进行启发式缓存，仍受缓存规则约束 可以通过明确的缓存信息允许缓存
POST 跟随行为 允许客户端改为 GET 允许客户端改为 GET

服务器通常通过 Location 指出新地址，客户端跟随时会发起新的 HTTP 请求。永久与临时是主要区别，不能简单理解为“301 一定缓存、302 一定不缓存”。

如果必须保留请求方法和请求体语义，临时重定向使用 307，永久重定向使用 308。爬虫处理跳转时，应限制跳转次数、检查目标地址，并按新地址重新匹配 Cookie，避免向不应接收的目标转发认证信息。

7. 404、500、502、403 状态码的含义

状态码 标准含义 常见例子
404 Not Found 服务器没有找到目标资源，或不愿透露其存在 URL 写错、资源已删除
500 Internal Server Error 服务器遇到意外情况，无法完成请求 未处理异常、内部处理失败
502 Bad Gateway 服务器作为网关或代理时，从上游收到无效响应 反向代理收到上游畸形响应，或上游连接异常中断导致无法得到有效响应
403 Forbidden 服务器理解请求，但拒绝处理 访问策略拒绝、账号权限不足

403 不要求用户已经登录；缺少有效认证凭据通常对应 401。502 侧重网关与上游之间的响应问题，网关等待上游响应超时通常对应 504。

在爬虫中，不能看到 403 就直接断定是 IP 被封，也不能把 500 一概归因于自己的参数错误，应结合响应内容和具体请求判断。
